# Идея (отложена): LLM-стадия пост-обработки транскрипта

**Статус:** зафиксировано, не реализовано (backlog). Вернуться по запросу.
**Дата фиксации:** 2026-06-21
**Ветка на момент фиксации:** `feat/transcriber-impl`

## Суть

После транскрипции+диаризации автоматически прогонять результат через LLM-агента,
который **в зависимости от содержания встречи** готовит структурированный документ:
протокол / структурирование требований / описание процесса / краткое резюме.

```
видео → аудио → транскрипция → диаризация → файлы → [НОВОЕ] analyze (LLM) → <имя>.<цель>.md
```

## Подтверждённая осуществимость (де-рискинг выполнен)

`claude` CLI установлен (`/c/Users/Romandredan/.local/bin/claude`, v2.1.183) и умеет
**headless-режим**: `claude -p` со стдином = промпт. Авторизация берётся из **подписки
пользователя**, БЕЗ платного API-ключа. Живой тест прошёл: на вход реплику встречи,
на выход — `РЕШЕНИЕ: Реализовать обмен заказами между InSales и 1С через REST API —
ответственный Иван, срок неделя.` (exit 0).

Значит приложение может вызывать `claude -p` как под-процесс, передавать
шаблон+транскрипт через stdin и получать готовый документ из stdout.

## Принятые решения (из брейншторма с пользователем)

| Вопрос | Решение |
|--------|---------|
| Провайдер LLM | **Claude через подписку** (`claude` CLI headless), без API-ключа. За абстракцией — потом можно добавить локальную модель / платный API. |
| Выбор «цели» | **Авто + ручной**: по умолчанию LLM сам классифицирует тип встречи и берёт шаблон; в UI можно переопределить (дропдаун). |
| Шаблоны (первый набор) | Протокол встречи; Структурирование требований; Описание процесса; Краткое резюме. |

## Эскиз архитектуры (для будущей реализации)

- **Новая опциональная стадия `analyze`** после `writers` (выключена по умолчанию).
- **Компонент `analyzer`** за интерфейсом `LLMProvider` (как `TranscriptEngine`):
  - `classify(transcript) -> purpose` — один дешёвый вызов (если режим «авто»): вернуть один из {protocol, requirements, process, summary, other}.
  - `analyze(transcript, purpose) -> markdown` — вызов с промптом выбранной цели.
  - Реализация по умолчанию: `ClaudeCliProvider` — пайпит `prompt+transcript` в `claude -p`, читает stdout.
- **Шаблоны** в редактируемой папке `prompts/` (`protocol.md`, `requirements.md`, `process.md`, `summary.md`); промпт классификатора перечисляет доступные цели.
- **UI**: per-job дропдаун «Цель обработки: Авто / Протокол / Требования / Процесс / Резюме / Выкл» + глобальный дефолт в настройках.
- **Настройки/.env**: `ANALYZE_ENABLED`, цель по умолчанию, `LLM_PROVIDER=claude_cli`, опц. `LLM_MODEL`.
- **Выход**: `output/<id>/<имя>.<purpose>.md` (+ опц. DOCX). Виден в UI рядом с транскриптом.
- **Надёжность (best-effort)**: если анализ упал — транскрипт уже сохранён, job не падает, ошибка в лог (как сделано для диаризации через `apply_diarization`).

## Открытые вопросы / нюансы к проработке при реализации

1. **Изолированный вызов `claude`.** Запускать из нейтрального cwd (или с флагами,
   отключающими project-настройки), чтобы headless-инстанс НЕ цеплял чужие
   `CLAUDE.md`/хуки/скиллы (напр. 1С-хуки TradeProd). Возможно `--allowed-tools`
   пустой или системный промпт, ограничивающий агента чистой генерацией текста.
2. **Приватность.** Через подписку транскрипт всё равно уходит в Anthropic (не локально).
   Для строго конфиденциальных встреч — локальный провайдер (Ollama/llama.cpp) за той же
   абстракцией. Отдельная задача.
3. **Лимиты подписки.** Пакетная обработка многих длинных встреч может упереться в лимиты
   Pro/Max. Возможна очередь/троттлинг.
4. **Длинные транскрипты.** Часовой транскрипт = много токенов. Claude тянет большой
   контекст; для очень длинных — map-reduce (по частям → сводка).
5. **Формат вызова.** Уточнить флаги `claude -p` (модель `--model`, формат вывода,
   ограничение инструментов, таймауты, обработка ошибок/непустой stderr).
6. **Версионирование результатов** при повторной обработке той же встречи с другой целью.
