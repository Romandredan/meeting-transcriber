# Дизайн: автоматический транскрибатор записей встреч

**Дата:** 2026-06-21
**Статус:** утверждён к реализации
**Расположение проекта:** `H:\.GitHub\meeting-transcriber` (отдельный репозиторий, не связан с TradeProd)

## 1. Назначение и контекст

Локальное single-user приложение для Windows, которое автоматически превращает видео-/аудиозаписи встреч в диаризованную транскрипцию с таймкодами. Файлы появляются локально (на том же диске), приложение их забирает, извлекает аудио через ffmpeg, прогоняет через Whisper на GPU, делает диаризацию и выдаёт пул файлов в нескольких форматах.

### Целевое окружение (зафиксировано замерами)

- **GPU:** NVIDIA GeForce RTX 5070 Ti, 16 ГБ VRAM, драйвер 581.80, архитектура Blackwell (sm_120).
- **ffmpeg:** 8.0.1 уже установлен и в PATH (проверка/автоустановка всё равно нужна для переносимости).
- **Python:** системный 3.14.0 — **не подходит** под ML-стек (нет wheels). Под ML создаётся отдельный venv на **Python 3.10–3.13** (на машине автора есть 3.10 — используется он; `install.ps1` для публичных юзеров предпочитает 3.12).

## 2. Ключевые решения (принятые в брейншторме)

| Решение | Выбор | Обоснование |
|---------|-------|-------------|
| Движок | **WhisperX** (faster-whisper + pyannote) | GPU, word-level таймкоды, реальная диаризация на русском, словарь через `initial_prompt` |
| Диаризация | **pyannote.audio 3.1** (HF-токен) | Полноценная диаризация N спикеров; токен будет получен |
| Деплой | **Нативно на Windows**, venv Python 3.10–3.13 (dev на 3.10) | Прямой доступ к GPU без прослоек |
| Расположение | **Отдельная папка/репозиторий** | Не смешивать с 1С TradeProd |
| Фронтенд | **Лёгкий SPA на vanilla JS** | Ноль сборки, FastAPI отдаёт одну HTML-страницу |
| Модель по умолчанию | **large-v3-turbo** (переключаемая) | Баланс скорость/точность для пакетной обработки |
| Форматы вывода | **TXT (таймкоды+спикеры), SRT, VTT, JSON, Markdown, DOCX** | Все выбраны |
| Очередь | **Последовательно, 1 файл** | Одна модель полностью грузит GPU; стабильнее по памяти |
| Подача файлов | **Watched-папка `inbox/` + UI по локальным путям** | Локальное решение — byte-upload не нужен |
| Триггер | **Встроенный watcher (`watchdog`), НЕ cron** | Сервис живёт постоянно, держит тёплую модель; cron перезагружал бы модель на каждый файл |

## 3. Архитектура

Один постоянно работающий процесс **FastAPI** (бэкенд + раздача статики + встроенный файловый watcher), очередь на **SQLite**, один последовательный GPU-воркер, движок WhisperX. ML-стек в отдельном venv Python 3.12.

```
        ┌─────────────────────────────────────────────────────┐
        │            Процесс FastAPI (постоянный)              │
inbox/ ─┤  watcher(watchdog) ──┐                               │
        │                      ▼                               │
Браузер─┤  SPA ──HTTP/SSE──► API ──► SQLite (очередь/настройки/история)
 (пути) │   прогресс ◄──SSE──────────┐                         │
        │                            ▼                         │
        │              GPU-воркер (1 поток, последовательно)   │
        │       ffmpeg → engine(transcribe→align→diarize)      │
        │                            ▼                         │
        │              output/<job>/ (txt,srt,vtt,json,md,docx)│
        └─────────────────────────────────────────────────────┘
```

### Поток данных одного job

1. Источник: файл появился в `inbox/` (watcher) **или** выбран по локальному пути в UI.
2. Watcher ждёт стабилизации размера файла N секунд (чтобы не схватить ещё копируемый файл), затем кладёт job в SQLite-очередь.
3. ffmpeg извлекает аудио → 16 kHz mono WAV (`-ar 16000 -ac 1 -c:a pcm_s16le`) во временную папку.

   > **Почему именно 16 kHz mono, а не выше.** Это не урезанное качество, а ровно вход, на котором обучен Whisper: модели внутри считают log-Mel спектрограмму из 16 kHz mono и сами ресемплят более высокую частоту вниз до 16 kHz — прироста точности от 44.1/48 kHz нет, только лишний размер и I/O. «128» — это битрейт сжатых форматов (MP3/AAC); WAV — несжатый PCM (lossless), 16 kHz mono 16-bit ≈ 256 kbps без потерь. Внутренние «128 mel-каналов» у `large-v3` — параметр модели, к входному аудио отношения не имеет.
4. faster-whisper транскрибирует (GPU, float16, `initial_prompt` = словарь).
5. Выравнивание слов по таймкодам.
6. pyannote-диаризация (если включена) → сшивка спикеров со словами.
7. `writers` пишут все выбранные форматы в `output/<job>/`.
8. Статус `done`, файлы доступны на скачивание (per-format + zip).

## 4. Компоненты (изолированные юниты)

| Юнит | Назначение | Зависит от |
|------|-----------|-----------|
| `ffmpeg_tool` | Детект ffmpeg в PATH; при отсутствии — скачать static-сборку / инструкция. Извлечение аудио 16 kHz mono. | ffmpeg |
| `engine` | Обёртка движка за единым интерфейсом: загрузка/кэш модели, `transcribe→align→diarize`, нормализованный результат-сегменты. Содержит развилку primary/fallback (§6). | faster-whisper, pyannote, torch(cu128) |
| `queue` | SQLite-очередь: job'ы, статусы (`queued/processing/done/error`), прогресс, история. Переживает рестарт. | sqlite3 |
| `worker` | Один фоновый поток: берёт job, гоняет конвейер, шлёт прогресс в SSE, ловит ошибки. | engine, ffmpeg_tool, writers |
| `watcher` | `watchdog`-наблюдатель за `inbox/`: стабилизация файла → enqueue. | watchdog, queue |
| `writers` | Сериализация результата в TXT, SRT, VTT, JSON, Markdown, DOCX. | python-docx |
| `api` | FastAPI: добавить job по пути, CRUD job'ов, настройки, SSE-прогресс, скачивание (+zip). | queue, worker |
| `web` | SPA: drag-drop/обзор по путям, список очереди с прогрессом, панель настроек, скачивание. | api |
| `settings` | Глобальные дефолты + per-job override: модель, язык, диаризация on/off, число спикеров, словарь. | sqlite3 |

Принцип: каждый юнит имеет одну ответственность, общается через явный интерфейс, тестируется независимо. `engine` прячет за интерфейсом выбор бэкенда (CT2 vs PyTorch-native), чтобы fallback не протекал в остальной код.

## 5. Веб-интерфейс

- **Добавление файлов:** drag-drop передаёт *локальный путь*; либо «обзор» по папке. Альтернатива — просто бросить в `inbox/`. Без byte-upload.
- **Очередь:** каждая запись — карточка со статусом и прогресс-баром по этапам (audio → transcribe → diarize → write).
- **Панель настроек** (глобальная + переопределение на job): модель (`turbo`/`large-v3`/…), язык (авто/ru/…), диаризация on/off, ожидаемое число спикеров (или авто), **словарь** (textarea с предупреждением про лимит, §7).
- **Прогресс:** SSE (однонаправленный поток — проще WebSocket).
- **Скачивание:** per-job каждый формат отдельно + «скачать всё .zip»; пул результатов виден списком.

## 6. Риск GPU и лестница fallback (критично)

**WhisperX гоняет инференс на CTranslate2, не на PyTorch.** Поддержка новых архитектур в CT2 исторически отстаёт, а RTX 5070 Ti (sm_120, Blackwell) — свежий кремний. Поэтому первой задачей реализации идёт **de-risking spike**, и только его результат подтверждает основной движок.

### Задача №1 — GPU-spike (до очереди/API/фронтенда)

1. Создать venv Python 3.10–3.13 (dev — 3.10).
2. Поставить `ctranslate2` + `faster-whisper` + `torch` из индекса **cu128** (Blackwell требует cu128-сборку PyTorch).
3. Прогнать клип 10 сек через faster-whisper `device="cuda", compute_type="float16"`.
4. В `nvidia-smi` убедиться, что реально исполняется на GPU (нет тихого отката на CPU, нет ошибки).
5. В том же spike проверить **pyannote на GPU** (та же PyTorch-зависимость).

**Ожидаемая засада:** cuDNN 9.x — может понадобиться wheel `nvidia-cudnn-cu12`. Симптомы: «Could not load cudnn» или «no kernel image is available» (sm_120).

### Лестница движка

1. **Основной:** faster-whisper / CTranslate2 (cu128).
2. **Fallback (если CT2 не берёт Blackwell):** **PyTorch-native Whisper** через `transformers` (`WhisperForConditionalGeneration`, `large-v3-turbo`) + pyannote — всё на одном стеке PyTorch cu128. Word-таймкоды через `return_timestamps="word"`. Не добавляет новых зависимостей сверх тех, что нужны pyannote.

**whisper.cpp исключён** из дизайна по решению: его диаризация непригодна (2 спикера, EN), pyannote всё равно обязателен, а самописная сшивка + сборка из исходников под Blackwell сложнее, чем готовый fallback на PyTorch.

Диаризация — pyannote в обоих вариантах движка.

### VRAM

Не закладываем сложное управление: turbo (CT2, fp16) ~1.5–2 ГБ, large-v3 ~3 ГБ, pyannote — сотни МБ. На 16 ГБ всё помещается. Достаточно загрузить модель один раз и держать тёплой; сложного VRAM-жонглирования не нужно.

### Автодетект устройства (для публичной дистрибуции)

Поскольку приложение выкладывается в открытый доступ и должно работать не только на Blackwell, движок **не прибивает `cuda` жёстко**: единый хелпер выбирает устройство — `cuda` → `compute_type=float16`, иначе **CPU-фолбэк** `cpu` → `compute_type=int8` (медленно, но работает на машинах без NVIDIA). pyannote аналогично переносится на доступное устройство. На целевой машине автора (RTX 5070 Ti) выбирается GPU-путь.

## 7. «Словарь» — честное ограничение

Маппится на Whisper `initial_prompt`: **лимит ~224 токена**. Длинный глоссарий молча обрежется, и он **смещает** распознавание, а не гарантирует термины. Это отражается и в дизайне, и в подсказке в UI (рядом с textarea). Возможное расширение позже (не в первой версии): пост-обработка find/replace по известным терминам.

## 8. Обработка ошибок

- ffmpeg не найден → явное сообщение + автоскачивание static-сборки; job не падает молча.
- Файл не медиа / нет аудиодорожки → job в `error` с понятным текстом, очередь продолжает.
- Файл ещё копируется → watcher ждёт стабилизации размера, не хватает раньше времени.
- OOM/ошибка GPU → ловим, job `error`, выгружаем модель при необходимости, следующий job продолжает.
- Падение процесса → SQLite хранит очередь; при старте «зависшие» `processing`-job'ы возвращаются в `queued`.

## 9. Тестирование

- **Юнит:** `writers` (форматы из фикстуры-результата), `queue` (переходы статусов, восстановление после рестарта), `ffmpeg_tool` (детект), `watcher` (стабилизация → enqueue).
- **Интеграционный:** короткий тестовый клип (10–20 с, 2 спикера) → полный конвейер → все форматы присутствуют и текст непустой.
- **Приёмочный для движка:** GPU-spike из §6.

## 10. Технологический стек

Python 3.12 venv · FastAPI + Uvicorn · vanilla-JS SPA · SQLite · WhisperX (faster-whisper + pyannote) с PyTorch-native fallback · ffmpeg · python-docx · watchdog. Дефолт модели — `large-v3-turbo`.

## 12. Дистрибуция и установка (публичный GitHub-релиз)

Приложение публикуется на GitHub для общего пользования. Реальность класса «Python + CUDA + тяжёлый ML»: «тихий .exe-установщик» невозможен/нецелесообразен (torch GPU ~2.5 ГБ и зависит от индекса под конкретную CUDA; модели качаются в рантайме; принятие условий gated-pyannote — неустранимый ручной шаг). Поэтому выбран **управляемый bootstrap-скрипт**, а не заморозка в exe.

**Целевые платформы v1:** Windows + NVIDIA (основная), CPU-фолбэк (медленно, но работает). Linux — вне v1.

**Механизм установки:**
- `install.ps1` (Windows): проверяет/ставит Python 3.12 (winget) и ffmpeg (winget) при отсутствии; **детектит GPU** (`nvidia-smi`) и выбирает torch-индекс: NVIDIA → `cu128`, иначе CPU-сборка torch; создаёт venv, ставит зависимости; копирует `.env.example` → `.env`.
- `run.ps1`: активирует venv и запускает `uvicorn app.main:app`.
- `install.sh`/`run.sh` — тонкие аналоги для будущего Linux (заготовка, не цель v1).
- **Запуск без HF-токена возможен:** транскрипция работает «из коробки», диаризация — опциональна и включается после получения токена (порог входа ниже).
- **Сеть настраивается через `.env`:** `APP_HOST` (дефолт `127.0.0.1`) и `APP_PORT` (дефолт **8473** — намеренно нечастый, чтобы не конфликтовать с типовым 8000). Приложение запускается через `python -m app.main` и берёт хост/порт из конфига; реальная env-переменная перекрывает `.env`, аргумент `run.ps1 <порт>` — поверх всего.

**Для релиза также:** `LICENSE` (напр. MIT), раздел README про установку/токен/требования, `.env.example`. Модели и venv — в `.gitignore` (уже учтено).

## 11. Вне рамок первой версии (YAGNI)

- Браузерные byte-upload'ы с удалённых машин (chunked-upload) — не нужно для локального решения.
- Параллельная обработка нескольких файлов — один GPU, последовательность стабильнее.
- Пост-обработка словаря find/replace — возможное расширение позже.
- Многопользовательский доступ, аутентификация.
