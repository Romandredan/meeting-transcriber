# AGENTS.md

Этот файл — руководство для AI-агентов, работающих с репозиторием. Читатель ничего не знает о проекте.

## Что это за проект

**Meeting Transcriber** — локальный транскрибатор записей встреч под **Windows + NVIDIA GPU**. Видео/аудиофайл → диаризованная (с разметкой спикеров) транскрипция с таймкодами в форматах TXT/SRT/VTT/JSON/MD/DOCX → опциональный анализ транскрипта локальной LLM (Ollama + `qwen3:14b`). Всё работает локально, ничего не отправляется наружу.

- Пользователь — не разработчик: веб-интерфейс на `http://127.0.0.1:8473`, установка и автозапуск — PowerShell-скриптами.
- Без NVIDIA GPU работает на CPU (значительно медленнее). Диаризация опциональна и требует HuggingFace-токен (`HF_TOKEN` в `.env`) с принятыми условиями `pyannote/speaker-diarization-community-1`; без токена молча пропускается.

## Технологический стек

- **Python 3.10–3.13**, стандартный `venv` в `.venv/` (системный python не подойдёт).
- **FastAPI + uvicorn** — веб-сервер и REST API ([app/api.py](app/api.py)); прогресс в UI — через SSE.
- **faster-whisper (CTranslate2)** — основной движок транскрипции на CUDA; **transformers** — экспериментальный PyTorch-native fallback.
- **pyannote.audio 4.x** — диаризация.
- **ffmpeg** — извлечение WAV из видео/аудио (ставится через winget при установке).
- **Ollama** — локальная LLM для стадии analyze (через нативный API Ollama, не OpenAI-совместимый).
- **SQLite** (stdlib `sqlite3`, файл `data.db`) — и очередь задач, и источник истины.
- Фронтенд — **vanilla JS без сборки**: [web/app.js](web/app.js), [web/index.html](web/index.html), [web/style.css](web/style.css).
- Осознанно используются stdlib-инструменты: HTTP-клиент — `urllib`, БД — `sqlite3`. **Новые зависимости добавляются неохотно** — сначала проверь, нет ли решения на stdlib или уже подключённых пакетах.

Зависимости (pyproject.toml нет):

- `requirements-base.txt` — fastapi, uvicorn, watchdog, python-docx, pytest, httpx.
- `requirements-ml.txt` — ctranslate2, faster-whisper, pyannote.audio, transformers. **Перед ними** torch ставится отдельной командой: `pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu128`.

## Архитектура

**Один процесс**: FastAPI-приложение + один фоновый worker-поток + watcher папки inbox. SQLite (`data.db`) — и очередь, и источник истины. Всё связывается в [app/main.py](app/main.py) на уровне модуля (импорт = запуск). Точка входа: `python -m app.main`.

### Конвейер транскрипции

1. Watcher ([app/watcher.py](app/watcher.py)) ждёт, пока файл в `inbox/` перестанет меняться (`INBOX_QUIET_SECONDS`).
2. Создаётся строка в таблице `jobs`; Worker ([app/worker.py](app/worker.py)) забирает FIFO.
3. ffmpeg извлекает WAV → `engine.transcribe()` → результаты пишутся в `output/<job_id>/` ([app/writers.py](app/writers.py)), исходник уезжает в `processed/`.

### Ключевые модули (`app/`)

- `engine/base.py` — интерфейс `TranscriptEngine`; реализации: `engine/faster_whisper_engine.py` (основной) и `engine/transformers_engine.py` (экспериментальный); выбор в `engine/factory.py` по наличию ctranslate2.
- `diarize.py` — диаризация pyannote; `stitch.py` — склейка реплик спикеров в абзацы.
- `db.py`, `job_queue.py` — схема БД и очередь транскрипций; `analyses.py` — очередь анализов. Схема эволюционирует **миграциями** (`MIGRATIONS` в `db.py`, версия в `PRAGMA user_version`): базовый блок `SCHEMA` заморожен, любое изменение схемы — новая миграция. Отмена работы кооперативная: флаг в памяти (`request_cancel`/`cancel_requested`/`clear_cancel`), воркер проверяет его на границе стадий в `report()` и бросает `JobCancelled` → статус `cancelled`; `delete()` убирает встречу, её анализы и алиасы спикеров, файлы в `output/` не трогает (чистка — только через API с `purge=true`).
- `speakers.py` — имена и объединения спикеров (таблица `speaker_aliases`, миграция 1). Сырые метки диаризации (`SPEAKER_00`) живут только в JSON на диске; алиасы и слияния (`merged_into`) применяются **на чтении** (`apply_view`: сырая метка → «Спикер 1» → слияние → имя) в API, при входе анализа и при перегенерации файлов. `stitch.humanize_speaker` идемпотентен: «очеловечивает» только сырые метки вида `SPEAKER_00`, готовые «Спикер N» и имена (даже с цифрами) пропускает как есть.
- `analyze.py` — детерминированный map-reduce конвейер анализа транскрипта (оценка токенов 2.4 симв./токен — эмпирика для русского; перекрытие чанков).
- `llm.py` — `OllamaProvider` через нативный API Ollama (OpenAI-совместимый эндпоинт не принимает `num_ctx`/`keep_alive`). Таймаут LLM — по простою (сокетный): пока идут токены, ждём сколько угодно.
- `templates_store.py`, `settings_store.py` — шаблоны анализа и настройки в БД (переживают перезапуск).
- `progress.py` — `ProgressBroker` → SSE → веб-интерфейс.
- `config.py` — сам читает `.env` (без python-dotenv) в модульные константы; `device.py` — выбор CUDA/CPU; `ffmpeg_tool.py` — обёртка над ffmpeg; `models.py` — управление кэшем моделей.

### Стадия analyze (опциональна, `ANALYZE_ENABLED`)

Отдельная очередь-таблица `analyses`, обрабатывается тем же единственным worker-потоком — так GPU-работы сериализуются сами собой. **Порядок выгрузок из VRAM обязателен**: `engine.unload()` (Whisper) ДО первого вызова LLM — qwen3:14b рядом с large-v3 в 16 ГБ не помещается; `provider.unload()` (`keep_alive=0`) ПОСЛЕ — чтобы карта была свободна под следующий Whisper.

### Инварианты, которые нельзя ломать

- **БД — источник истины, файлы — best-effort копии.** Результат анализа сначала сохраняется в БД (`result_md`); запись `.md` на диск — best-effort и не роняет job при сбое. Тот же принцип у `move_to_processed` и всех `unload()`.
- **Миграции схемы БД.** Изменение схемы = новая запись в конец `MIGRATIONS` в `db.py` (версия = `PRAGMA user_version`). Уже выпущенную миграцию **не редактировать** — у пользователей она применена. Шаг по возможности идемпотентен (`CREATE ... IF NOT EXISTS`; `ADD COLUMN` — после проверки `PRAGMA table_info`). Каждая миграция применяется в своей транзакции, сбой откатывает её и не повышает версию.
- **Алиасы спикеров — на чтении.** Имена и слияния (`speaker_aliases`) никогда не переписывают сырой JSON; применяются через `speakers.apply_view` (слияние → имя) в выдаче транскрипта, входе анализа и перегенерации файлов. Слияния — один уровень (цепочки запрещены валидацией). Перегенерация TXT/SRT/VTT/MD/DOCX после `PUT speakers` — best-effort (истина — алиасы в БД). Анализ, сделанный до переименования, — снимок: не меняется, только перегенерация новой версии.
- **Снимок промпта:** анализ хранит `prompt_snapshot` — копию текста шаблона на момент запуска, не ссылку на шаблон. Правка шаблона не должна менять историю.
- **UI:** при автообновлении не сбрасывать состояние пользователя (выбранный шаблон, раскрытые `<details>`) — эта грабля уже наступалась не раз.
- **Выгрузка при простое:** `IDLE_UNLOAD_SECONDS` — обе очереди пусты N секунд → все модели выгружаются из VRAM (программа живёт в автозапуске и не должна держать видеопамять между встречами). `0` — не выгружать.

## Тестирование

- Разработка через **TDD**; на каждый модуль `app/X.py` есть `tests/test_X.py` — при добавлении модуля добавляй и тест-файл.
- Тесты **не требуют GPU, сети и Ollama**: всё внешнее подменяется фейками из [tests/fakes.py](tests/fakes.py) (FakeProvider и др.) и in-memory SQLite.
- Перед сдачей работы обязательно: `.venv\Scripts\python -m pytest -q` — весь набор должен быть зелёным.

## Соглашения по коду

- **Русский язык везде**: комментарии, докстринги, тексты коммитов (conventional commits с русским описанием: `fix(worker): ...`), и особенно **тексты ошибок** — они показываются пользователю-неразработчику и должны быть понятны ему (например, `json.JSONDecodeError` перехватывается ради русской формулировки).
- Комментарии в коде объясняют «почему», часто с историей решения — поддерживай этот стиль.
- Метки шаблонов анализа идут в имена файлов на диске, поэтому валидируются как `[a-zA-Z0-9_-]{1,32}` ([app/api.py](app/api.py)).
- Новые настройки документируются в [.env.example](.env.example) — это основная пользовательская документация настроек; `config.py` читает `.env` сам, через `os.environ.setdefault` (существующие переменные не перезаписываются).
- Изменения должны быть минимальными: не рефакторить и не «причёсывать» код вокруг задачи.

## Установка и деплой (для пользователя)

- Точка входа для клиента — **батники в корне**: `Установить.bat`, `Запустить.bat`, `Диагностика.bat`, `Обновить.bat`. Они **строго ASCII (включая комментарии!)**: cmd парсит .bat в консольной кодировке, и UTF-8-кириллица (даже в `rem`) сбивает его парсер на многобайтовых символах — проверено опытом. Весь русский вывод живёт в `.ps1`.
- Все `.ps1` — **обязательно UTF-8 с BOM**: без BOM PowerShell 5.1 читает русский текст как cp1251 и вывод превращается в кракозябры.
- `install.ps1` — идемпотентная установка: Python и ffmpeg (winget, без winget — прямое скачивание с python.org / gyan.dev в `tools/ffmpeg`), torch под GPU/CPU, Ollama + `ollama pull $LLM_MODEL` + переменные демона `OLLAMA_FLASH_ATTENTION`/`OLLAMA_KV_CACHE_TYPE`, предзагрузка моделей через `scripts/warmup_models.py`, интерактивный ввод HF_TOKEN. Каждая внешняя команда проверяется по `$LASTEXITCODE` (EAP=Stop их НЕ ловит), сбой → русское сообщение + `logs\install.log`, который пользователь прикладывает к issue. Флаги: `-Autostart` / `-NoAutostart` / `-SkipOllama`.
- Автозапуск — задача Планировщика «при входе» (`register-autostart.ps1` / `unregister-autostart.ps1`), без ExecutionTimeLimit. `autostart.ps1` — **супервизор**: перезапуск сервера при падении, анти-зацикливание (5 падений за 10 минут → стоп с записью в лог), ротация логов (5 поколений `logs\server.out.log.N`), проверка «уже запущен» по порту. Задача работает в пользовательской сессии — это нужно для доступа к GPU.
- `run.ps1 [порт]` — ручной запуск из `.venv`; при занятом порте печатает «уже запущено» и выходит, а не роняет uvicorn traceback'ом.
- `diag.ps1` — сбор диагностики в `logs\diag-<дата>.zip` для приложения к issue (без секретов: `.env` не включается, только факт наличия HF_TOKEN); `update.ps1` — `git pull` + переустановка зависимостей + перезапуск сервера (данные пользователя не трогает).

## Соображения безопасности

- `.env` содержит `HF_TOKEN` и **не коммитится** (в `.gitignore`); в репозитории — только `.env.example` с пустым токеном. Никогда не читай и не выводи содержимое `.env` без необходимости. Это касается и диагностики: `diag.ps1` сознательно не включает `.env` в архив.
- По умолчанию сервер слушает `127.0.0.1` (только локальная машина); `APP_HOST=0.0.0.0` открывает доступ из локальной сети — осознанная настройка пользователя.
- Всё обрабатывается локально: аудио, транскрипты и LLM-анализ наружу не уходят — не добавляй код, отправляющий пользовательские данные во внешние сервисы.

## Структура каталогов

- `app/` — весь бэкенд (модули перечислены выше); `app/engine/` — движки транскрипции.
- `web/` — фронтенд без сборки.
- `tests/` — pytest-тесты, зеркалят модули `app/`.
- `docs/` — внутренние дизайн-документы и планы (`docs/ideas/`, `docs/superpowers/`, `docs/plan-easy-install.md`). Всё это в `.gitignore` и существует только у автора: в клоне репозитория каталога может не быть — не ссылайся на него в коде и публичной документации.
- `inbox/`, `output/`, `processed/`, `tmp/` — рабочие каталоги конвейера (переопределяются в `.env`).
- `models/` — кэш моделей HuggingFace; `logs/` — логи сервера и установки, diag-архивы; `scripts/` — разовые скрипты (`warmup_models.py` — предзагрузка моделей установщиком, `spike_gpu.py`).
- `tools/` — создаётся установщиком при fallback-установке ffmpeg (в git не входит).
- `data.db` — SQLite с очередями и результатами (в git не входит).
